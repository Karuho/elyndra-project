## Release objective

Build the first large, disk-backed Spanish linguistic core for Alejandría so Elyndra can understand,
normalize and relate common Spanish words, senses, forms, synonyms, antonyms and informal internet
language locally before consulting Ollama.

The release must reduce unnecessary tutor use for ordinary vocabulary while preserving:

- sense-aware interpretation;
- account isolation;
- bounded RAM use;
- source provenance;
- licensing compliance;
- CLI/web parity;
- reviewable user-specific learning;
- no runtime network access.

This release is a linguistic-resource and retrieval release, not a general reasoning-model upgrade.

## Product rationale

A tutor-only strategy is inefficient for common language. Elyndra should be able to perform the same
basic operation a human performs with a dictionary: look up a word, identify possible senses, inspect
relations and use that information to interpret a sentence.

Examples:

- `frío` may mean low temperature or emotionally distant behavior.
- `helado` may be a food noun or an adjective meaning extremely cold.
- `congelado` may describe a physical state, a financial account or figurative inactivity.
- `np`, `idk`, `xfa`, `hdp`, `xD`, `jajaja`, `jsjsjs` and common emojis belong to informal registers.
- `jdsjsdjsdajsad` may be laughter-like keyboard expression, but arbitrary random text must not always
  be classified as laughter.

The system must represent senses and context instead of performing global synonym replacement.

## Verified source policy as of August 2026

### Eligible source: Spanish WordNet / MCR 3.0

The official Spanish and Catalan WordNets licensing page states that the MCR 3.0 Spanish WordNet was
built from scratch, is linked to WordNet 3.0, and is distributed under CC BY 3.0 for commercial and
research use.

Reference:

- https://nlp.lsi.upc.edu/esWN/licenseWN.php

Requirements:

- verify the license file or notice shipped with the actual downloaded artifact;
- record CC BY 3.0 attribution in the pack manifest;
- preserve source version and checksum;
- do not import older Spanish WordNet releases with different commercial/research licenses.

### Eligible source with share-alike obligations: Spanish Wiktionary

Wikimedia text is reusable under CC BY-SA 4.0 and, depending on the content/history, GFDL or additional
compatible attribution requirements may also apply.

References:

- https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use
- https://dumps.wikimedia.org/eswiktionary/

Requirements:

- keep Wiktionary-derived data in a separately licensed data pack;
- generate complete source attribution and license notices;
- preserve the dump date and SHA-256;
- identify transformations performed by Elyndra;
- do not copy Wikimedia logos or imply endorsement;
- do not relicense Wiktionary-derived content as the Elyndra code license.

`wiktextract` may be used as an optional build-time extractor if Codex confirms the exact installed
version and license. Its project is MIT licensed, while extracted data remains subject to Wiktionary's
content licenses.

Reference:

- https://github.com/tatuylonen/wiktextract

### Optional eligible source: Unicode CLDR emoji annotations

Unicode CLDR provides localized names and keywords for emoji. If included, use a pinned stable release
and preserve the Unicode Data Files and Software License notice.

References:

- https://cldr.unicode.org/index/downloads
- https://www.unicode.org/copyright.html

CLDR is optional for this release. Do not block the Spanish lexical core if CLDR integration requires
additional review.

### Project-authored source: informal Spanish internet register

Elyndra may include a small, original, reviewed register file authored in this repository for:

- common abbreviations;
- discourse markers;
- laughter patterns;
- keyboard-expression patterns;
- common emoticons;
- selected emoji pragmatic labels.

This source must not be copied from proprietary slang dictionaries. It must include explicit ambiguity,
register and confidence fields.

### Prohibited sources

Do not import or reproduce RAE, Oxford or other proprietary dictionary content unless a compatible
license is supplied and explicitly approved.

## Release deliverables

### 1. Shared Spanish language-pack architecture

Create a shared, read-only language-pack location outside account vaults, for example:

```text
~/.local/share/elyndra/language-packs/es/<pack-id>/
├── elyndra-language-pack.json
├── lexicon.sqlite
├── ATTRIBUTION.md
└── LICENSES/
```

The exact location should follow current `ElyndraPaths` conventions.

Shared packs contain no personal data. Account-specific reviewed corrections remain in the account vault.

### 2. Language-pack registry

Advance the root schema from `48` to `49`, unless repository inspection identifies a conflict.

Add a small root registry for installed packs. Suggested tables:

```text
alexandria_language_packs
alexandria_language_pack_sources
```

Registry fields should include:

- public ID;
- language and locale;
- pack version;
- pack schema version;
- status: `installed`, `enabled`, `disabled`, `invalid`;
- absolute or root-relative private path;
- manifest SHA-256;
- pack database SHA-256;
- source count;
- lexical/sense counts;
- created/imported timestamps;
- builder version;
- verification status and last verification time.

Do not copy the lexical dataset into the root database or account vaults.

### 3. Pack manifest

Define `elyndra-language-pack.json`, schema version `1`.

Required fields:

```json
{
  "schema": 1,
  "pack_id": "...",
  "language": "es",
  "locale": "es",
  "version": "...",
  "builder_version": "0.8.8-alpha",
  "database_sha256": "...",
  "counts": {},
  "sources": [],
  "limitations": [],
  "created_at": "..."
}
```

Each source entry must contain:

- source ID and title;
- source version/date;
- source URL;
- local input filename;
- original SHA-256;
- license identifier and license text path;
- attribution text;
- transformation notes;
- imported record counts.

Reject installation when required source licensing or checksums are absent.

### 4. Separate lexical SQLite pack

The generated SQLite database should contain normalized, indexed data. Suggested tables:

```text
lexemes
lexeme_forms
synsets
senses
synset_members
sense_definitions
sense_examples
sense_relations
synset_relations
usage_labels
informal_entries
emoji_annotations
source_records
```

Required concepts:

- lemma;
- normalized lemma;
- language/locale;
- part of speech;
- grammatical features;
- form type and inflection metadata;
- sense and synset identity;
- definitions;
- examples when licensing permits;
- synonyms via synset membership;
- antonyms;
- hypernyms/hyponyms;
- meronymy/holonymy when available;
- derivational and related-term links;
- domain and usage labels;
- register: formal, neutral, colloquial, vulgar, internet, regional;
- provenance per record.

Add FTS5 indexes for lemmas, forms and definitions when the local SQLite build supports FTS5. Fail with
a clear diagnostic if FTS5 is unavailable; do not silently build a degraded full pack.

### 5. Safe, streaming import pipeline

Implement local-file importers. Runtime network access remains disabled.

Minimum supported inputs:

1. Spanish WordNet-LMF XML or the exact locally downloaded MCR Spanish WordNet format.
2. A structured Wiktionary JSONL input produced by an approved extractor.
3. The project-authored informal Spanish register JSON/JSONL.
4. Optional CLDR Spanish emoji annotation XML/JSON.

Import requirements:

- inspect before build;
- reject symlinks and path traversal;
- reject missing licenses/checksums;
- bound individual file and record sizes;
- stream records rather than loading all data into memory;
- use transactions and batched inserts;
- build in a temporary private directory;
- finalize with atomic rename;
- deterministic IDs derived from source plus stable external identifiers;
- deterministic output for identical inputs and builder version;
- do not execute templates, JavaScript, macros or imported code;
- imported definitions/examples are data, never instructions.

If direct Wiktionary dump extraction is too large for the release, implement and document a pinned
optional build step using `wiktextract`, but the Elyndra importer itself must consume a stable JSONL
contract and remain testable without network or the full dump.

### 6. Informal Spanish and internet-language core

Add a small reviewed source file in the repository for common informal expressions.

The schema should support:

- expression;
- normalized form;
- expansion or meaning;
- language/locale;
- register;
- category;
- ambiguity notes;
- confidence;
- examples written specifically for Elyndra;
- offensive/vulgar flag;
- source=`elyndra_curated`.

Initial coverage should include representative items, not an unreviewed exhaustive slang list:

- `xfa`, `porfa`, `porfis`;
- `np`, `idk`, `imo`, `tbh`, `afaik`;
- `hdp` marked vulgar/offensive and context-dependent;
- `lol`, `lmao`, `xD`, `XD`;
- repeated Spanish laughter such as `jajaja`, `jejeje`, `jsjsjs`;
- laughter-like keyboard patterns such as `jdsjsdjsdajsad` with conservative heuristics;
- emoticons such as `:)`, `:(`, `:D`, `-_-`;
- common discourse markers such as `onda`, `tipo`, `igual`, `literal` with sense/register notes.

Do not treat every random keyboard sequence as laughter. A sequence like `asdfghjkl` should remain
unknown/keyboard-smash unless contextual evidence supports a pragmatic interpretation.

### 7. Emoji semantics

At minimum, support:

- exact emoji sequence;
- Spanish short name;
- keywords;
- broad pragmatic categories;
- ambiguity notes.

Do not equate emoji with a definitive emotional state. For example, `😭` may express sadness,
exaggeration or laughter depending on context.

If CLDR is not included in the first implementation, include only a small original fixture/core and keep
CLDR import as an implemented but optional source adapter.

### 8. Lexical query service

Create a bounded service/repository that can:

- exact lemma lookup;
- inflected-form lookup;
- prefix/FTS lookup;
- sense lookup;
- synonyms for a selected sense;
- antonyms for a selected sense;
- semantic relations;
- informal expression lookup;
- emoji annotation lookup;
- unknown-term detection.

Requirements:

- no entire pack loaded into RAM;
- bounded connection/page/cache behavior;
- result limits and query timeouts where practical;
- stable ordering;
- source attribution in results;
- pack verification before use;
- disabled or invalid packs are never queried.

### 9. Sense-aware semantic integration

Integrate the lexical service with `SemanticIntentRepository` and the conversational path.

Rules:

1. Exact deterministic phrases remain first.
2. Approved account-specific intent examples remain high priority.
3. Spanish lexical normalization may expand candidate terms only within a strict budget.
4. Synonyms are applied by sense/POS when enough context exists.
5. Ambiguous lexical expansion must lower confidence or request clarification.
6. Antonyms inform contrast but never become synonyms.
7. Informal-language normalization may help intent resolution.
8. If the local lexicon resolves the vocabulary but not the user's intent, the tutor may still classify
   the intent.
9. If the word is absent, the tutor may propose an interpretation but may not write directly to the
   shared language pack.
10. User corrections continue through the reviewed language-learning proposal flow.

No naive global replacement such as `frío → helado` across every context.

### 10. Conversational behavior

Expected examples:

#### Vocabulary lookup

```text
Usuario: ¿Qué significa onomatopeya?
Elyndra: definición local, sentidos y fuente; sin Ollama cuando el pack is sufficient.
```

#### Synonyms and antonyms

```text
Usuario: dame sinónimos de frío
Elyndra: asks or groups by sense when necessary:
- temperatura: helado, gélido...
- trato: distante, indiferente...
```

```text
Usuario: cuál es el antónimo de frío
Elyndra: caliente for the temperature sense; cálido/afectuoso for interpersonal senses.
```

#### Internet language

```text
Usuario: idk xfa revisa esto
```

Elyndra should normalize `idk` and `xfa` locally before intent resolution.

```text
Usuario: jdsjsdjsdajsad
```

Elyndra may classify it as likely laughter/paralinguistic expression with bounded confidence rather than
as a literal unknown word, but it must not treat all random strings the same way.

#### Emoji

```text
Usuario: 😭
```

Elyndra should recognize the emoji and retain ambiguity; it must not diagnose sadness from the emoji
alone.

### 11. CLI surface

Exact names may be adapted to current CLI conventions, but provide equivalent operations:

```bash
elyndra alexandria language-pack inspect PATH
elyndra alexandria language-pack build-es \
  --wordnet-lmf PATH \
  --wiktionary-jsonl PATH \
  --informal-source PATH \
  --cldr-annotations PATH \
  --output-dir PATH \
  --approve
elyndra alexandria language-pack install PATH --approve
elyndra alexandria language-pack list
elyndra alexandria language-pack show ID
elyndra alexandria language-pack verify ID
elyndra alexandria language-pack enable ID --approve
elyndra alexandria language-pack disable ID --approve
elyndra dictionary lookup "frío" --language es --relations
elyndra dictionary senses "frío" --language es
elyndra dictionary related "frío" --relation synonym --sense ID
elyndra assistant understand "idk xfa revisa esto"
```

Do not implement pack deletion in this release. Disable is sufficient.

### 12. Web surface and parity

Developer mode:

- Alejandría > Idiomas panel;
- installed Spanish pack status;
- source/license attribution;
- counts and verification state;
- inspect/install/enable/disable flows with explicit confirmation;
- lexical lookup diagnostics;
- semantic-resolution debug showing lexical contribution without private reasoning.

User mode:

- natural dictionary questions through chat;
- optional simple dictionary lookup UI;
- no pack paths, schema details or technical source controls;
- source attribution visible in an understandable form.

All web writes require authenticated account, developer mode where appropriate, CSRF/session checks and
explicit approval.

### 13. Account-specific language overlays

Shared packs are immutable/read-only after installation.

Reviewed account-specific corrections remain in the account vault and may override or supplement lookup
for that account without changing the shared pack.

Do not allow one account's slang correction, preferred usage or semantic learning to affect another
account.

### 14. Performance and memory

- Do not load the full lexicon into RAM.
- Use SQLite indexes and bounded caches.
- Keep any in-process lexical cache small and configurable.
- Stream import data.
- Provide counts and elapsed time after builds.
- Record peak-memory observations during a representative fixture/full-source build when possible.
- A failed build must leave no half-installed enabled pack.

Full-pack performance targets are observational rather than hard CI requirements:

- exact warm lookup should normally feel interactive;
- ordinary queries should return a bounded number of senses/relations;
- semantic resolution should not enumerate large synonym graphs.

## Out of scope

Do not implement in `0.8.8-alpha`:

- English full lexical pack;
- Controlled Online Gateway;
- runtime downloading of dictionaries;
- direct model internet access;
- remote telemetry;
- remote backup/account recovery;
- active 2FA;
- automatic promotion of tutor vocabulary into the shared pack;
- speech recognition or TTS;
- embeddings or vector databases as a requirement;
- a full grammar parser;
- pack deletion;
- proprietary dictionary sources.

## Security requirements

- No runtime network.
- No `shell=True`.
- No imported code execution.
- No unsafe XML entities.
- No symlink/path escape.
- No zip/decompression bombs.
- Bound source sizes, record sizes, relation fan-out and result counts.
- Treat definitions/examples as untrusted content.
- Never insert imported text into system instructions.
- Verify checksums before build/install/use.
- Keep generated files private and finalize atomically.
- Shared pack must be opened read-only during normal query operation.

## Acceptance criteria

The release is complete only when all are true:

1. The repository contains a documented, tested language-pack format and local import pipeline.
2. A fixture Spanish pack builds deterministically and installs atomically.
3. A real locally supplied Spanish WordNet source can be imported or the exact blocker is documented.
4. A structured Wiktionary JSONL source can be imported with attribution and share-alike metadata.
5. Exact and form lookups are disk-backed and bounded.
6. Synonyms and antonyms are sense-aware.
7. Informal Spanish and common internet expressions improve semantic resolution locally.
8. Emoji annotations retain ambiguity and do not infer diagnoses.
9. Tutor use decreases for covered vocabulary but remains available for unresolved intent.
10. Shared packs contain no account data.
11. Account-specific overlays remain isolated.
12. CLI and web use the same service.
13. User mode cannot manage packs.
14. Runtime remains offline and no telemetry is sent.
15. Migration from schema 48 preserves all prior data.
16. All mandatory documentation is updated.
17. All tests and quality checks pass.
