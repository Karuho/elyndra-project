# Elyndra 0.8.10-alpha — Autonomous Development Runtime specification

## Status and validated baseline

Elyndra 0.8.10-alpha is an in-development supervised autonomous-development
runtime. It extends the immutable released 0.8.9-alpha baseline without
changing the deny-by-default authority model.

Current validated feature-branch baseline after Phase 7B.1:

- branch: `feat/0.8.10-autonomous-development-runtime`;
- commit: `ba84909ffbb6e43bfce24e18cadb040f7406cd1f`;
- visible development version: `0.8.10-alpha`;
- root/vault schema: `56`;
- language pack schema: `1`;
- language bundle schema: `1`;
- registered skills: `102`;
- tests: `880`;
- test files: `88`;
- Bubblewrap is the sole real autonomous process-execution boundary;
- external networking remains unavailable to the autonomous runtime;
- execution observations are durable and provenance-bound.

This specification is normative for the remainder of 0.8.10-alpha.

## Objective

Build a bounded, capability-based development runtime that can eventually
perform supervised development work on an explicitly selected workspace
without allowing a language model to acquire authority merely by requesting it.

The runtime must be able to progress from a frozen plan through controlled
execution, durable observation, reviewable file modification, validation and
repair while preserving explicit authority boundaries and human control.

The target interaction is eventually equivalent to:

1. receive an owner-approved development objective;
2. derive or accept a bounded frozen plan;
3. operate only inside an exact approved workspace;
4. use only explicitly granted capabilities;
5. execute only frozen and validated commands;
6. persist real observations and outcomes;
7. propose or apply only separately authorized self-modification;
8. validate resulting changes;
9. stop or request human review when authority, evidence or policy is
   insufficient;
10. never silently expand its own authority.

## Core authority invariant

The model is not an authority source.

Model, tutor, planner or generated text may propose actions, code, explanations
or plans, but may never:

- issue a `CapabilityGrant`;
- enlarge a `WorkspaceScope`;
- approve a `HumanGate`;
- manufacture execution reservations;
- manufacture launch provenance;
- authorize network access;
- authorize Git or GitHub publication;
- bypass a failed or indeterminate execution state;
- grant self-modification merely by emitting code;
- convert observations into new authority.

Authority originates only from trusted Elyndra runtime state and explicit
owner-approved policy.

## Non-objectives

0.8.10-alpha does not introduce:

- unrestricted autonomous operation;
- hidden or persistent background development;
- automatic Internet access;
- direct model network access;
- arbitrary shell execution;
- `shell=True`;
- unrestricted subprocess launch;
- unbounded retries;
- silent self-repair loops;
- silent self-modification;
- automatic package installation;
- automatic Git commit, push, tag or release;
- automatic privilege escalation;
- implicit reuse of approvals;
- authority derived from stdout, stderr or model output;
- remote telemetry;
- rewriting of the immutable `v0.8.9-alpha` release.

Any later background operation requires a separately reviewed phase and must
reuse the same bounded authority model.

## Trusted and untrusted boundaries

Trusted application components include the deterministic Elyndra autonomy
runtime, repository validation, capability enforcement and approved execution
boundary.

Untrusted inputs include:

- language-model output;
- tutor output;
- planner suggestions;
- stdout and stderr from child processes;
- files modified by executed tools;
- imported project text;
- test output as semantic input;
- external content if networking is introduced by a later approved release.

Bubblewrap child-process output is an observation, not authority.

An opaque execution-observation receipt proves provenance through Elyndra's
trusted executor path. It is not cryptographic attestation of the child
process, operating system or executable semantics.

## Architecture

The 0.8.10 autonomy runtime is composed around the following durable domain
objects:

- `AutonomyRun`;
- `WorkspaceScope`;
- `CapabilityGrant`;
- `RunPlan`;
- `RunStep`;
- `HumanGate`;
- `CommandSpec`;
- `CommandSnapshot`;
- `ExecutionRequest`;
- `PreparedExecution`;
- `ExecutionResult`.

The trusted flow is:

    owner authority
        |
        v
    CapabilityGrant + WorkspaceScope
        |
        v
    frozen RunPlan / RunStep
        |
        v
    AutonomyExecutionBinding
        |
        v
    ExecutionContract.prepare()
        |
        v
    durable reservation
        |
        v
    BubblewrapExecutor
        |
        +--> one-shot durable launch
        |
        +--> bounded process
        |
        v
    durable execution observation
        |
        v
    supervised orchestration

No planner or model chooses Bubblewrap flags, process primitives, reservation
identity, observation receipts or durable authority state.

## Phase history

### Phase 1 — bounded autonomy foundation

Completed.

Introduced the bounded autonomy domain, workspace scopes, capabilities, frozen
plans, human gates and core invariants.

No process execution or autonomous continuation was introduced.

### Phase 2 — durable autonomy state and audit

Completed.

Persisted runs, events and HumanGates in append-only audited state.

Authority remains explicit and owner-scoped.

### Phase 3 — controlled execution contract

Completed.

Defined the pure execution contract and executor protocol without adding a real
process implementation.

### Phase 4 — persisted authority binding

Completed.

Added `AutonomyExecutionBinding`, reconstructing execution authority only from
trusted persisted run state, frozen grants, plans, workspace scopes and audited
HumanGate approvals.

### Phase 5 — durable execution reservations

Completed.

Added append-only execution-budget reservations with durable command, retry and
runtime accounting.

Reservations consume bounded grant budget.

### Phase 6A.1 — frozen autonomous command domain

Completed.

Added deterministic `CommandSpec`, executable identity, environment/sandbox
profiles and immutable command snapshots.

Direct arbitrary scripts remain outside the allowed command domain.

### Phase 6A.2 — command authority binding

Completed.

Bound allowed executable authority into capability grants and persisted frozen
process steps.

### Phase 6A.3 — reservation-to-command snapshot binding

Completed.

Bound every process reservation to the exact frozen command snapshot and
command hash.

### Phase 7A — sandboxed autonomous process execution

Completed.

Added `BubblewrapExecutor` as the sole real autonomous process boundary.

The sandbox:

- launches only through trusted `/usr/bin/bwrap`;
- uses `shell=False`;
- clears inherited environment;
- drops capabilities;
- unshares namespaces;
- denies external network access;
- exposes only the exact workspace as writable;
- binds system runtime paths read-only;
- uses a sealed initial executable snapshot;
- bounds stdout and stderr;
- enforces timeout and cancellation;
- consumes every request ID at most once.

A consumed launch is never replayed.

### Phase 7B.1 — durable execution observations

Completed at
`ba84909ffbb6e43bfce24e18cadb040f7406cd1f`.

Added schema 56 durable append-only execution results.

Each fresh launch receives a CSPRNG opaque observation receipt. SQLite stores
only a request-bound domain-separated SHA-256 commitment. Result persistence
requires matching executor-path provenance using constant-time comparison.

The runtime records:

- exact request and command identity;
- outcome;
- exit code;
- duration;
- bounded stdout/stderr;
- hashes;
- timeout/truncation metadata;
- retry state.

Audit events exclude raw process output and caller-controlled summaries.

A launch with no durable result is represented explicitly as
`observation_unresolved`.

The runtime does not guess whether such a process succeeded or failed.

## Phase 7B.2 — supervised one-tick runner

Next approved phase.

Add a synchronous supervised runner with the invariant:

> one tick performs zero or one process launch.

A tick must:

1. verify run ownership and executable state;
2. detect incomplete durable attempts before doing new work;
3. bind authority through `AutonomyExecutionBinding`;
4. derive progress only from frozen plan order and durable results;
5. select only the first incomplete step;
6. support `PROCESS_EXEC` only in this phase;
7. prepare one exact execution;
8. execute it through `BubblewrapExecutor`;
9. return immediately after that one execution;
10. optionally mark the run completed if every frozen step has a durable
    successful observation.

It must not:

- loop;
- recurse into another tick;
- automatically retry;
- skip an unsupported or failed step;
- execute a later step while an earlier one is unresolved;
- synthesize results;
- create authority;
- broaden a grant or workspace;
- execute network, Git or self-modification capabilities.

### Incomplete attempts

The runner must fail closed for either:

    reservation exists -> launch missing

or:

    launch exists -> result missing

These states are durable and distinct.

No automatic retry follows either state.

### Concurrent initial execution

Only one initial reservation may exist for one run/step pair.

A second request ID attempting another initial reservation for that same step
must be denied without consuming more budget.

Retry semantics remain outside Phase 7B.2.

## Phase 7B.3 — reviewed failure and retry semantics

Planned after 7B.2 validation.

Define explicit owner-reviewed handling for failed, cancelled and indeterminate
attempts.

Requirements include:

- no automatic retry;
- every retry uses a fresh request ID;
- every retry consumes new durable retry/runtime/command budget;
- retry permission must be explicit and bounded;
- one HumanGate approval must not silently authorize an unlimited number of
  retries;
- indeterminate launch state cannot be converted into success or failure.

The exact approval-consumption design must be reviewed before implementation.

## Phase 7C — bounded multi-step orchestration

Planned.

Allow deliberate continuation across multiple ticks while preserving:

- one execution per tick;
- durable progress recovery;
- bounded maximum steps;
- bounded commands;
- bounded runtime;
- bounded retries;
- fail-closed unsupported capabilities;
- stop conditions;
- HumanGate boundaries.

This phase must not introduce hidden background execution.

## Phase 8 — transactional self-modification

Planned only after supervised orchestration is stable.

Self-modification must use a separate capability and must be transactional.

Required properties include:

- exact approved workspace;
- frozen file-change intent;
- bounded changed-file set;
- no path or symlink escape;
- recoverable pre-change state;
- deterministic diff;
- validation before promotion;
- rollback on failed validation when safe;
- explicit distinction between proposed, applied, validated and rejected
  state;
- no authority expansion caused by modified code;
- no automatic Git publication.

The model may propose source changes but cannot grant `SELF_MODIFY`.

## Phase 9 — evaluation and supervised repair

Planned.

Use durable execution and validation observations to propose repair steps.

Failure output remains untrusted data.

Repair must remain bounded by the original objective, workspace and authority.
It may not convert a failed test into permission for unrelated changes.

No unbounded repair loop is permitted.

## Background execution

Long-running or background autonomous development is explicitly outside the
currently approved implementation phases.

It may be considered only after:

- supervised one-tick execution;
- retry semantics;
- orchestration;
- transactional self-modification;
- repair;
- crash recovery;
- locking;
- shutdown behavior;
- resource accounting;
- audit behavior

are independently validated.

## Process security invariants

- `BubblewrapExecutor` remains the only real autonomous process boundary.
- `shell=True` is forbidden.
- The initial executable identity is frozen and validated.
- Command working directory remains inside the exact workspace.
- Executable and command hashes remain bound through reservation and launch.
- Process execution remains deny-by-default.
- Child output cannot issue commands or authority.
- stdout/stderr stay bounded in bytes.
- invalid UTF-8 is sanitized without exceeding byte limits.
- timeouts and cancellation remain bounded.
- a request ID launches at most once.
- launch provenance secrets are never persisted in plaintext.
- launch/result ledgers remain append-only.

## Network invariants

The autonomous development runtime has no external networking in the current
approved scope.

`0.8.9-alpha` Controlled Online Gateway authority is not inherited by autonomy.

A grant for process execution does not imply network authority.

The model, planner and child process cannot request or manufacture a network
capability.

Any future autonomous network integration requires a separate specification,
allowlisted hosts, explicit capability and dedicated tests.

## Git and GitHub invariants

Git/GitHub capabilities are distinct from workspace/process capability.

Until a later phase explicitly implements them:

- the autonomous runner does not commit;
- the autonomous runner does not push;
- the autonomous runner does not tag;
- the autonomous runner does not create releases;
- the autonomous runner does not rewrite history.

Development performed by external coding agents during implementation of
Elyndra is not itself Elyndra runtime authority.

## Crash consistency

Durable state is authoritative across process restarts.

At minimum, the runtime distinguishes:

- no reservation;
- reservation but no launch;
- launch but no durable result;
- durable succeeded result;
- durable failed result;
- durable cancelled result.

It must never infer missing state as success.

A consumed request is not silently replayed after a crash.

## Audit and privacy

Autonomy audit must remain structured and bounded.

Do not persist:

- raw language-model chain of thought;
- approval secrets;
- observation receipt secrets;
- credentials;
- environment secrets;
- unbounded command output.

Process stdout/stderr may exist only in the bounded execution-result ledger
where explicitly designed. Audit events use hashes and deterministic metadata
rather than copying raw output.

## Schema

Current target root/vault schema is 56 after Phase 7B.1.

Phase 7B.2 does not require a schema change.

Every later schema change must:

- be forward-only;
- migrate from the exact previous schema;
- preserve existing rows;
- be transactionally tested;
- preserve append-only authority history where applicable.

Language-pack and language-bundle schemas remain 1.

## CLI and web

The autonomous-development runtime is an internal/developer feature while its
security and orchestration architecture is under construction.

No user-facing CLI/web execution parity is required for the internal Phase
7A/7B primitives unless a phase explicitly promotes them to a public product
surface.

When a user-facing autonomy surface is introduced, CLI and web must share the
same underlying service and authority policy.

## Validation policy

Every implementation phase requires focused tests for its own security
invariants.

Before a phase is committed, run:

    python -m compileall -q src tests
    python -m ruff check .
    python -m pytest -q
    git diff --check

The full test suite must contain zero skips unless a separately documented,
owner-approved platform limitation explicitly requires otherwise.

Real Bubblewrap execution must be validated on a compatible Linux host rather
than replaced by mocks that weaken security coverage.

## Phase 7B.2 acceptance criteria

Phase 7B.2 is accepted only if tests prove:

- one tick launches at most one process;
- a two-step plan requires separate ticks;
- final successful progress can mark the run completed;
- completed/non-running runs do not execute;
- failed/cancelled results block later automatic progress;
- reservation-without-launch fails closed;
- launch-without-result fails closed;
- concurrent/different request IDs cannot create duplicate initial step
  reservations;
- denied duplicate reservations consume no additional budget;
- unsupported capability is not skipped;
- actor mismatch cannot execute;
- arbitrary executor/launcher injection is unavailable;
- Bubblewrap remains the sole process boundary;
- no `shell=True`;
- no network authority is introduced;
- schema remains 56.

## 0.8.10 release acceptance criteria

Before 0.8.10-alpha can be declared complete:

- every implemented phase has focused security regressions;
- the complete suite passes with no unexplained skips;
- no model output can grant authority;
- no execution path bypasses durable reservation and launch state;
- no process launch bypasses Bubblewrap;
- no replay of consumed request IDs is possible;
- crash/indeterminate states fail closed;
- self-modification, if included, is transactional and separately authorized;
- retries, if included, are fresh, bounded and explicitly reviewed;
- external networking remains absent unless separately specified;
- release documentation accurately describes final implemented scope;
- immutable 0.8.9-alpha history/tag remains unchanged.

## Release rejection criteria

Reject 0.8.10-alpha for any of the following:

- model-generated authority;
- implicit approval;
- automatic unlimited continuation;
- unrestricted shell or subprocess access;
- `shell=True`;
- workspace/symlink escape;
- executable identity bypass;
- duplicate or replayed process launch;
- silent retry after indeterminate execution;
- unbounded output or runtime;
- raw observation secrets persisted or audited;
- automatic network access;
- automatic Git/GitHub publication;
- unreviewed self-modification;
- failed migration preservation;
- weakening existing 0.8.9 security boundaries to enable autonomy.
